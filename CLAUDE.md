# Правила работы в репозитории

## Порядок работы

1. **Сначала теория, потом код.** Любая новая функциональность начинается с обсуждения и согласования решения. Реализация — только после утверждения владельцем продукта.
2. Значимое архитектурное решение оформляется как ADR в `instructions/adr/`. Утверждённый ADR не переписывается: изменение оформляется новым ADR, который заменяет старый.
3. Перед работой сверяйся с ADR. Если задача противоречит утверждённому решению, сначала обсуди это, а не обходи решение молча.

## Документация

- Все `.md` документы, кроме `README.md` и этого файла, лежат в `instructions/`.
- После добавления нового функционала обновляй `README.md`.

## Скрипты

- Тестовые и разовые утилитарные скрипты — только в `test-scripts/<сервис>/`, не внутри папок сервисов.

## Архитектурные правила (кратко, подробно в ADR)

- Новый функционал — это новый модуль с манифестом (ADR-003). Модуль можно включить, выключить и заблокировать. При блокировке в админке показывается модальное окно.
- Модуль не читает и не пишет чужие таблицы. Связь с другими модулями — через SDK или события.
- Отказ модуля не должен ронять ядро, а отказ ядра — публичный сайт (ADR-002).
- Модули обращаются к ядру только через наш SDK, не к API основы ядра напрямую (ADR-010).
- Ценная логика модуля лежит в `protected/` и собирается с защитой (ADR-009).

## Секреты

- Никаких секретов в репозитории. В git попадает только `.env.example`.
- Тестовые учётные данные — в seed-файлах проекта, не в документации.
