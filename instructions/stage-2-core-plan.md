# План этапа 2. Ядро ячейки

- **Статус:** утверждено 2026-10-29, включая порядок этапов, состав модулей и GHCR
- **Дата:** 2026-10-29
- **Основа:** ADR-002, ADR-003, ADR-005, ADR-006, ADR-009, ADR-011, ADR-012; [отчёт проверки Payload](spike-payload-report.md)
- **Срок по дорожной карте:** 4–6 недель, команда — владелец и ИИ

## 1. Цель

Одна ячейка проходит всю цепочку **на локальной машине**:

> создать ячейку → наполнить контент → подключить модули → собрать сайт (SSR и статика) → обновить ядро с откатом → бэкап и восстановление → архив передачи клиенту.

Это вертикальный срез из списка рисков дорожной карты: сначала вся цепочка на одном сайте, потом расширение вширь.

## 2. Что входит и что нет

Работаем локально, перенос существующих проектов не в фокусе (решение владельца от 2026-10-29).

| Входит | Не входит (позже) |
|---|---|
| Монорепозиторий, CI, образы | Раздел «Платформа» в renoteOS и `fleet-gateway` |
| Ядро на Payload 4 и модульная система | Настоящие серверы: `bootstrap` пишем, но проверяем только локально |
| Модули `forms`, `seo`, `redirects`, `legal` | Мигратор WordPress (этап 3) |
| SDK модулей и SDK сайта | Маркет, оплата (этап 4) |
| Стартер сайта: SSR и статика | Драйверы выкладки `ssh`, `sftp`, `ftps`, `git` |
| Worker очереди, бэкапы, восстановление | Контейнерные модули (`runtime: container`) |
| CLI `renote`: создание, обновление, бэкап, передача ячейки | |
| Agent, который сводит ячейку к желаемому состоянию из **локального файла** | Получение желаемого состояния из Платформы |
| `build:exit` с проверкой в CI | |

**Порядок этапов.** По дорожной карте этап 1 («Платформа в renoteOS») шёл раньше. Его основная польза — управление текущими клиентскими серверами и WordPress, а это сейчас не в фокусе. Решение владельца от 2026-10-29: сначала этап 2, этап 1 — после. Контракты с Платформой (`@renote/platform-contracts`) закладываются уже сейчас, чтобы потом не переделывать.

## 3. Структура репозитория

pnpm-монорепозиторий по ADR-001. Код проверки из ветки `spike/payload` — образец, переносится выборочно и с тестами.

```
core/                    ядро ячейки: Payload 4, адаптер модулей, health
worker/                  процесс очереди задач (тот же код ядра, другой вход)
modules/
  forms/ seo/ redirects/ legal/
packages/
  module-sdk/            defineModule, типы, runtime, тестовый стенд модулей
  site-sdk/              клиент сайта: типы контента, ISR, ревалидация
  platform-contracts/    желаемое состояние, телеметрия, события (Zod)
  eslint-config/         правила, включая запрет импортов для модулей
starters/site-node/      стартер уникального сайта, CLAUDE.md для ИИ
agent/                   reconciler: машина состояний обновления из v1
cli/                     renote: cell create / update / backup / restore / exit
deploy/                  шаблон compose ячейки, Caddy, bootstrap
test-scripts/            сценарии проверок по сервисам
instructions/            документация
```

## 4. Вехи

Каждая веха заканчивается проверяемым результатом и коммитом в `main`. Номера недель ориентировочные.

### Веха 1. Каркас (неделя 1)

- Монорепозиторий, TypeScript, ESLint, Vitest, Prettier.
- Ядро на Payload 4: точная версия, базовая модель контента (страницы с секциями, медиа, настройки сайта, пользователи с ролями).
- Только миграции, `push` — только в dev.
- **Worker** — отдельный процесс очереди задач (находка проверки: в веб-процессе очередь стартует только с первым запросом).
- Compose для разработки: ядро, worker, Postgres, MinIO.
- CI в GitHub Actions: проверка типов, линтер, тесты, сборка образов.

**Готово, когда:** `pnpm dev` поднимает ячейку, CI зелёный, health показывает ядро и worker.

### Веха 2. Модульная система (недели 1–2)

- `@renote/module-sdk` — из проверки, плюс:
  - манифест компилируется в сборку, а не читается с диска (находка проверки: иначе исходники модулей попадают в образ);
  - типизированные слаги коллекций и задач модуля;
  - маршруты упавшего модуля отвечают 503, а не 404;
  - тестовый стенд модуля: модуль поднимается на ядре в тесте.
- Адаптер в ядре: safe mode, бюджет фильтров, kill switch, лицензии, события через очередь в одной транзакции с данными, DLQ.
- Жизненный цикл ADR-003: `install → migrate → activate → deactivate → uninstall`, данные при удалении сохраняются.
- Модуль `forms` переносится из проверки с тестами.

**Готово, когда:** модуль можно поставить, выключить и удалить без потери данных; падение модуля не роняет ядро — это проверяют автотесты.

### Веха 3. Модули SEO, редиректы, legal (недели 2–3)

Логика переносится из прототипа v1 (ADR-011), около 1 400 строк, тесты пишутся при переносе.

- `seo`: мета-теги, Open Graph, `sitemap.xml`, `robots.txt`, хлебные крошки.
- `redirects`: правила 301/302, импорт списком, проверка на циклы.
- `legal`: политика конфиденциальности и другие документы, версии, согласия по 152-ФЗ.
- Точки расширения (`page.meta`, `sitemap.entries` и т. п.) выводятся из этих четырёх модулей и фиксируются в SDK (ADR-003).

**Готово, когда:** на сайте работают SEO-теги, sitemap, robots, редиректы и страница политики, всё управляется из админки.

### Веха 4. Стартер сайта (недели 3–4)

- `@renote/site-sdk`: типы из ядра, клиент, поддержка блоков модулей.
- Мгновенная ревалидация: ядро после публикации вызывает вебхук сайта (находка проверки: сейчас задержка до 60 с).
- Все опубликованные страницы собираются при сборке, страница ошибки с контактами при недоступном ядре.
- SSR и статика из одного кода, выбор режима по уровню сервера (ADR-005).
- `CLAUDE.md` и описание SDK для ИИ-агентов: новый сайт на стартере собирается быстро и без ошибок интеграции.

**Готово, когда:** демо-сайт собирается в обоих режимах; при остановленном ядре все страницы открываются.

### Веха 5. Эксплуатация ячейки (недели 4–5)

- Образы `core`, `worker`, `site-runtime` в приватном GHCR из CI.
- Шаблон compose ячейки с лимитами памяти (находка проверки: лимит — это и есть механизм бюджета).
- CLI `renote`:
  - `cell create` — секреты, compose, миграции, пресет модулей, первый администратор;
  - `cell backup` / `cell restore` — `pg_dump` и медиа в MinIO;
  - `cell update` — машина состояний из v1 со снапшотом и автооткатом.
- Agent: сводит ячейку к желаемому состоянию из локального файла (Платформа подключится позже через `platform-contracts`).
- Автоматическая проверка восстановления: бэкап поднимается во временной ячейке и проходит smoke-тест.

**Готово, когда:** обновление с ошибкой в миграции откатывается само, бэкап восстанавливается в новой ячейке.

### Веха 6. Передача и закалка (недели 5–6)

- `renote cell exit` — архив передачи из проверки, доведённый до процедуры ADR-009.
- **Обязательная проверка в CI:** в образе передачи нет исходников, source maps и строк из `protected/`.
- Закалка: ограничение попыток входа, защитные HTTP-заголовки, отсутствие учёток по умолчанию, двухфакторная аутентификация администраторов.
- Сквозной сценарий вертикального среза — один скрипт от `cell create` до архива передачи.

**Готово, когда:** сквозной сценарий проходит в CI.

## 5. Как работаем

- Каждая веха — короткая сводка тебе и коммит в `main` после проверки.
- Значимые решения внутри этапа оформляются новыми ADR.
- Тесты пишутся вместе с кодом. Для модулей обязательны тесты деградации (ADR-003).
- Код проверки не копируется целиком: берём решения, переписываем начисто.

## 6. Риски

| Риск | Что делаем |
|---|---|
| Payload 4 выйдет из беты с изменениями API | Payload спрятан в адаптере ядра и SDK; модули не меняются. Обновление — отдельной задачей |
| Этап растянется | Вехи 1–4 дают рабочее ядро с сайтом даже без вех 5–6. Порядок вех — по ценности |
| Точки расширения окажутся неудачными | Выводим их из четырёх реальных модулей, а не придумываем заранее |
| Локальная проверка не покажет проблем настоящего сервера | `bootstrap` и агент проверяем на сервере сразу, как появится задача с реальным клиентом |

## 7. Что нужно от владельца

1. Утвердить порядок: этап 2 раньше этапа 1.
2. Утвердить состав модулей: `forms`, `seo`, `redirects`, `legal`.
3. Для вехи 5 нужен приватный реестр образов. Предлагаю GHCR в том же GitHub-аккаунте. Если репозиторий приватный, CI тратит минуты GitHub Actions: бесплатного лимита на нашем объёме, скорее всего, хватит.
