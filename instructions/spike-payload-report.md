## 3. Ограничения и обходные пути

| Ограничение | Причина | Что делаем |
|---|---|---|
| Синхронный код модуля нельзя прервать по бюджету | Свойство Node | `inprocess` — только наши модули; всё чужое — `container` (ADR-003) |
| Изоляция модуля внутри процесса — соглашение | Один процесс | SDK без доступа к Payload, запрет импортов в ESLint, ревью и подпись |
| В dev-режиме `push` может удалить таблицы упавшего модуля | Drizzle push | В ячейках только миграции. Проверено: в production таблицы целы |
| Маршруты упавшего модуля отвечают 404, а не 503 | Не регистрируются | Регистрировать заглушки с 503 |
| Очередь задач стартует только с первым REST-запросом | Ленивая инициализация Payload | Отдельный процесс worker в ячейке (ADR-002) |
| Трассировка Next кладёт исходники модулей в образ | Манифесты читаются с диска | Компилировать манифесты в сборку; шаг CI «в образе передачи нет исходников» |
| Проверку лицензии можно пропатчить в бандле | Код работает у клиента | Слои 1 и 4 ADR-009; водяной знак для расследования |
| Строки в байт-коде читаются | Свойство байт-кода V8 | Не хранить секреты в `protected/`; защита — повышение цены разбора |
| Страница, которую никто не открывал, падает при остановленном ядре | ISR собирает страницы по запросу | Собирать все страницы при сборке сайта, страница ошибки с контактами |
| Формы не работают при остановленном ядре | Формы ходят в ядро | Резервный приём заявок у Платформы (особенно для уровня L1) |
| Новая страница появляется на сайте с задержкой до 60 с | ISR | Вебхук ядра → `revalidateTag` у сайта |
| Слаги коллекций модулей не попадают в типы Payload | Генерация типов | Генерация типов на модуль в SDK |

## 4. Решение по версии: Payload 4

Проверка со второго дня шла на `4.0.0-beta.5`.

**За 4.0:**

- новый API плагинов `definePlugin` — основа нашего адаптера модулей. На 3.x адаптер пришлось бы переписывать через несколько месяцев;
- права проверяются и в серверном коде по умолчанию — безопаснее для модулей;
- очередь задач с захватом и арендой — основа outbox и уведомлений;
- первая ячейка продукта появится не раньше чем через 2–3 месяца: к этому времени 4.0, скорее всего, выйдет;
- за четыре дня работы на бете не встретилось ни одной ошибки самого Payload.

**Риски и как их держим:**

- `definePlugin` помечен `@experimental`, API беты может меняться. Модули зависят только от нашего SDK, Payload спрятан в адаптере ядра;
- версия фиксируется точно, обновление — через тесты совместимости модулей (ADR-003);
- если 4.0 не выйдет к первому пилоту — остаёмся на последней бете и обновляемся до релиза отдельной задачей.

## 5. Что меняется в ADR

ADR-010 не переписывается. Выбор ядра оформлен новым **[ADR-012](adr/ADR-012-core-payload-4.md)** (статус «предложено», нужно утверждение владельца). Он дополняет:

- ADR-002: в ячейке обязателен отдельный процесс worker для очереди; лимит памяти в compose — механизм бюджета, а не только защита;
- ADR-003: данные модуля — префикс таблиц `mod_<id>_`; маршруты модулей — `/api/m/<id>/`; в `protected/` только функции;
- ADR-006: схема в ячейке меняется только миграциями, `push` запрещён;
- ADR-009: шаг CI «в образе передачи нет исходников, source maps и строк из `protected/`».

## 6. Рекомендация и сроки

**Рекомендация:** утвердить ADR-012 и начинать этап 2 «Ядро ячейки» с чистого каркаса на Payload 4. Код проверки — образец, а не основа продукта.

**Влияние на дорожную карту:**

| Этап | Было | Стало | Почему |
|---|---|---|---|
| 2. Ядро ячейки | 4–6 нед. | 4–6 нед. | Подтверждены все механизмы. Добавились worker очереди, компиляция манифестов, вебхук ревалидации — они укладываются в срок за счёт готовых образцов |
| 3. Мигратор WordPress | 3–4 нед. | без изменений | Не проверялся, риск остаётся |
| 5. Передача | 2 нед. | 1–1,5 нед. | `build:exit` и архив передачи уже работают на прототипе |

Что осталось непроверенным:

- перенос WordPress-сайта (критерий 4);
- работа на реальном сервере в РФ: замеры сделаны на Mac с Docker Desktop;
- поведение при обновлении ядра под работающими модулями (тесты совместимости N-1 и N из ADR-003).
