# ADR-004. Слой доступов: токены, SFTP/FTP, SSH, хранилище секретов

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-005, ADR-009

## Контекст

- Сейчас проекты клиентов обслуживаются по SSH-ключам и FTP-доступам.
- Связь с данными клиента (сайт, админка) должна работать через токен, FTP или SSH.
- Доступами пользуются сотрудники агентства, клиент и подрядчики клиента. Владелец решил, что это **базовый функционал**: он есть и в Платформе, и в админке клиента.
- На общем сервере несколько ячеек. SSH к самому хост-серверу — это доступ ко всем клиентам сразу.

## Решение

### Единая модель доступа

Любой доступ — это запись с полями:

| Поле | Значение |
|---|---|
| `subject` | Кто: сотрудник, клиент, подрядчик, сервис, модуль |
| `resource` | К чему: ячейка, сервер, сайт клиента, каталог |
| `kind` | `token`, `sftp`, `ftps`, `ssh` |
| `scopes` | Какие права: `pages:read`, `media:write`, путь `media/` на запись |
| `expiresAt` | Срок действия. Бессрочные доступы — только у сервисов |
| `issuedBy` | Кто выдал |
| `lastUsedAt` | Последнее использование |

Любой доступ **отзывается одной кнопкой**. Каждое использование пишется в аудит.

Где управляется:

- **Платформа (CRM):** все доступы агентства ко всем проектам, учёт ключей и паролей к серверам клиентов, журнал «кто и когда заходил».
- **Админка клиента, раздел «Доступы»:** клиент выдаёт доступы своим подрядчикам в пределах своего проекта и видит доступы агентства.

### Токены (API)

| Тип | Префикс | Назначение |
|---|---|---|
| Personal Access Token | `rnt_pat_` | Человек: скрипты, интеграции |
| Service Token | `rnt_svc_` | Сайт, внешняя система, контейнерный модуль |
| Preview Token | `rnt_prv_` | Ссылка на черновик, короткий срок |
| Agent Token | `rnt_agt_` | Связь сервера с `fleet-gateway` |

- Префикс нужен, чтобы утёкший токен находили сканеры секретов (например, GitHub secret scanning).
- В БД хранится **только хеш** токена. Сам токен показывается один раз при выдаче.
- Скоупы обязательны. IP-allowlist — по желанию.
- Ротация без простоя: старый и новый ключи работают одновременно в течение окна.

### Файловый доступ: SFTPGo как шлюз

Один экземпляр **SFTPGo** на сервер, в многопользовательском режиме:

- **Протоколы:** SFTP (по умолчанию), FTPS для старых клиентов, WebDAV, веб-интерфейс.
- **Голый FTP без TLS запрещён:** пароль передаётся открытым текстом.
- **Изоляция:** каждый пользователь заперт в каталогах своей ячейки (`media/`, `theme/`, `exports/`) с правами на каждый каталог.
- **Управление:** REST API SFTPGo. Платформа и админка клиента создают и отзывают пользователей программно.
- **Аудит:** события SFTPGo пишутся в журнал. Загрузка в `media/` вызывает задачу, которая регистрирует файл в медиатеке.

### Shell: SSH через bastion

- **На хост общего сервера SSH не выдаётся никому, кроме администратора платформы.**
- Вход в ячейку идёт через bastion (jump-host) в **toolbox-контейнер ячейки**. В нём доступны:
  - CLI `renote` (миграции, кэш, модули, бэкап);
  - логи процессов ячейки;
  - `psql` только к БД этой ячейки.
- **Короткоживущие SSH-сертификаты.** CA находится в Платформе. Сертификат выдаётся кнопкой на 8 часов с principal конкретной ячейки. Увольнение сотрудника — это отзыв роли, а не обход серверов с удалением ключей.
- **Выделенный сервер клиента** — обычный SSH по сертификатам того же CA.

### Хранилище чужих учётных данных

Пароли и ключи к серверам и хостингам клиентов — **самые чувствительные данные системы**.

- **Envelope encryption.** У каждого проекта свой ключ данных (DEK). Он зашифрован мастер-ключом (KEK), который хранится вне БД. На старте KEK лежит в файле с правами `0400` на сервере CRM (sops/age), позже переезжает в Vault.
- **Секрет никогда не возвращается в UI после сохранения.** Видно только: задан, когда обновлён, когда последний раз успешно подключились.
- **Ключи вместо паролей.** Для SSH Платформа генерирует пару сама и показывает клиенту публичный ключ: «добавьте в `authorized_keys`». Пароль клиента не нужен.
- **Расшифровка только в worker** в момент выполнения задачи. В логи секреты не попадают: маскирование на уровне логгера.
- Ротация KEK возможна без перешифровки данных: перешифровываются только DEK.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Раздавать SSH к хосту и FTP через системных пользователей ОС | Нет изоляции ячеек, нет аудита, ключи разбросаны по серверам |
| Teleport как шлюз доступа | Мощно, но тяжело для одного разработчика. Вернуться при росте команды |
| Хранить пароли клиентов в CRM «как есть» | Одна утечка БД означает компрометацию всех клиентов |
| Писать свой FTP/SFTP-сервер | SFTPGo закрывает задачу, имеет API и аудит |

## Последствия

- Нужен модуль доступов в ядре ячейки (токены, интеграция с SFTPGo) и в Платформе (CA, хранилище, журнал).
- Обязательные регрессионные тесты безопасности: токен, FTP-пользователь, SSH-сертификат и модуль не выходят за границы своей ячейки.
- При передаче проекта (ADR-009) все доступы агентства отзываются, а секреты клиента передаются ему и уничтожаются у нас.
