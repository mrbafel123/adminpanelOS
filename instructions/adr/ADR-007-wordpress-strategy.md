# ADR-007. Стратегия по WordPress: сначала управление, затем миграция

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-004, ADR-005, ADR-008

## Контекст

- Большинство текущих клиентов работают на WordPress. Остальные — на самописных сайтах и других CMS.
- **Главная цель владельца** — полностью перевести клиентов с WordPress на свою систему.
- Доступ к сайтам клиентов сейчас есть по SSH или FTP (уровни L1–L2, ADR-005).
- Платформа будет готова не сразу, а польза нужна раньше.

## Решение

Применяем стратегию **постепенного вытеснения** (strangler fig) в два этапа.

### Этап A. Управление WordPress-сайтами из CRM

Раздел «Платформа → Сайты» работает с WordPress через SSH и `wp-cli`. Это **первая польза для агентства уже через 1,5 месяца**.

| Функция | Как |
|---|---|
| Инвентаризация | `wp core version`, `wp plugin list`, `wp theme list`, версии PHP и MySQL |
| Уязвимости | Сверка версий плагинов с открытой базой уязвимостей (WPScan, Patchstack или аналог; выбор при реализации). Найденная уязвимость → `Alert` в CRM |
| Бэкапы | `wp db export` + архив `wp-content` → S3 в РФ, по расписанию |
| Обновления | Бэкап → `wp plugin update` → HTTP-проверка ключевых страниц → откат из бэкапа при ошибке |
| Здоровье | Состояние из Uptime Ray (уже есть в CRM) + размер диска и ошибки PHP по SSH |

Для сайтов на уровне L1 (только FTP) доступны бэкап файлов и мониторинг.

**Попутный результат: аудит плагинов.** Сводка «какие плагины стоят у наших клиентов и сколько раз» определяет, какие модули делать первыми (ADR-008). Решения принимаются по данным, а не по рейтингу WordPress.org.

### Этап B. Миграция на платформу

Модуль-мигратор `wp-import` в ядре ячейки.

**Источники данных** — по убыванию полноты:

1. Прямой доступ к БД по SSH (дамп) — самый полный, видны все мета-поля.
2. WP REST API с application password.
3. Файл экспорта WXR — когда другого доступа нет.

**Что переносится:**

| WordPress | Платформа |
|---|---|
| Страницы, записи, иерархия | Коллекции контента |
| Рубрики, метки, свои таксономии | Таксономии |
| Медиатека | Медиа с сохранением alt и подписей. Ссылки в контенте переписываются на новые адреса |
| Поля ACF | Поля модели контента. Карта соответствий генерируется и правится разработчиком |
| SEO из Yoast или Rank Math | Модуль SEO: title, description, canonical, OG, noindex |
| Редиректы (плагин Redirection) | Модуль редиректов |
| Меню | Навигация |
| Пользователи-редакторы | Пользователи ячейки, с приглашением на смену пароля |

**Сохранение SEO — обязательное требование:**

- все старые URL сохраняются;
- для каждого изменившегося адреса автоматически создаётся 301-редирект;
- sitemap и robots воспроизводятся.

**Проверка перед переключением.** Краулер обходит старый и новый сайт и сравнивает:

- коды ответов;
- title и description;
- canonical;
- количество страниц в sitemap;
- битые ссылки и изображения.

Отчёт о расхождениях — обязательное условие переключения.

**Переключение и откат:**

1. Новый сайт работает на временном домене.
2. Клиент проверяет и подписывает.
3. DNS переключается.
4. Старый WordPress остаётся в режиме только чтения 30 дней. **Откат — вернуть DNS.**

### Другие CMS и самописные сайты

- Универсальный импорт из CSV или JSON по карте полей.
- Для сайтов без доступа к данным — сбор контента краулером с ручной доводкой.
- Делаем по мере появления таких клиентов, не в MVP.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Сразу мигрировать всех, без этапа управления | Месяцы без пользы, высокий риск ошибок на всех клиентах одновременно |
| Headless WordPress (оставить WP как бэкенд) | Не достигает цели владельца, оставляет уязвимости и обслуживание WordPress |
| Миграция вручную под каждого клиента | Не масштабируется, высокий риск потерь SEO |

## Последствия

- Слой доступов (ADR-004) и SSH-операции в worker Платформы нужны уже на этапе A. Он становится первым, что реализуется.
- Миграция — это отдельная платная услуга в CRM (`ServiceCatalog`).
- Первым мигрируемым должен быть простой сайт агентства или лояльного клиента.
