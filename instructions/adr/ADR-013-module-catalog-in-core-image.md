# ADR-013. Каталог модулей в образе ядра: установка — это включение

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Заменяет:** в ADR-003 — поле `migrations` манифеста и шаг `migrate` жизненного цикла; в ADR-006 — версии модулей в желаемом состоянии ячейки
- **Связанные:** ADR-003, ADR-006, ADR-008, ADR-009, ADR-012

## Контекст

ADR-003 предполагал, что у модуля своя цепочка миграций и модуль ставится в ячейку отдельно, своей версией. На Payload 4 (ADR-012) так не получается:

1. **Схема базы общая.** Каждая коллекция модуля добавляет колонки в служебные таблицы ядра (например, `payload_locked_documents_rels`). Payload ведёт одну цепочку миграций на всю схему, независимых миграций у модуля быть не может.
2. **Конфиг собирается при сборке.** Коллекции модулей входят в образ ядра, добавить модуль в работающую ячейку без новой сборки нельзя.

## Решение

1. **Образ ядра содержит каталог официальных модулей.** Схема всех модулей каталога создаётся одной цепочкой миграций ядра. Таблицы модуля есть в каждой ячейке, у неустановленного модуля они пустые.
2. **Установка — это включение в данных ячейки**, без пересборки и перезапуска. Состояние хранится в коллекции ядра `cell-modules`. Шаги: проверка лицензии и зависимостей → `onInstall` модуля → модуль появляется в админке, работают его маршруты, фильтры и подписки.
3. **Удаление — это выключение.** Модуль скрывается из админки, его маршруты отвечают 503, фильтры и подписки не вызываются. **Данные сохраняются.** Стирание данных — отдельное явное действие с бэкапом (этап 2, веха 5).
4. **Версия модуля совпадает с версией образа ядра.** Модули выходят вместе с релизом ядра и тестируются вместе. Kill switch (ADR-003) по-прежнему действует точечно — на модуль или его версию.
5. **Манифест `module.yaml` компилируется в сборку.** Скрипт каталога проверяет манифесты и генерирует TypeScript-файл каталога. С диска во время работы ничего не читается: так исходники модулей не попадают в образ (находка проверки Payload).
6. **В архив передачи входят только купленные модули** (ADR-009). Код остальных модулей в сборку передачи не попадает, их пустые таблицы безвредны.
7. **Сторонние модули и модули под одного клиента** работают в режиме `container` (ADR-003) и этим решением не затрагиваются.

## Жизненный цикл модуля (вместо ADR-003)

`в каталоге → install → active ⇄ degraded → uninstall (данные сохранены) → install снова`

Отдельно от него: `failed` (safe mode при сбое запуска) и `disabled` (kill switch).

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Свой образ на каждую ячейку с набором модулей | У каждой комбинации своя цепочка миграций. Генерировать миграции при сборке без ревью опасно |
| Свой механизм миграций модулей в обход Payload | Модули всё равно меняют служебные таблицы ядра — хрупкая надстройка |
| Модули с отдельными версиями внутри одного образа | Та же проблема общей схемы, плюс комбинаторика тестов совместимости |

## Последствия

- Установка мгновенная — подходит для кнопки в маркете (ADR-008).
- Одна проверенная цепочка миграций, без автогенерации на сервере.
- Модуль нельзя обновить отдельно от ядра. Срочное исправление модуля — патч-релиз ядра.
- В базе каждой ячейки лежат пустые таблицы неустановленных модулей.
- В желаемом состоянии ячейки (ADR-006) поле `modules` хранит список установленных модулей без версий: `modules: [seo, forms]`.
