# ADR-009. Передача проекта клиенту и защита кода

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-003, ADR-004, ADR-006, ADR-008

## Контекст

Если клиент уходит, агентство обязано передать ему полностью рабочий сайт и админку. Условия передачи:

- дальше клиент обслуживает систему сам;
- **все связи с ядром платформы удаляются**;
- **с переданной админкой нельзя ничего сделать и ничего из неё вытащить**: защита кода агентства.

Инженерное ограничение: код, работающий на сервере клиента, **невозможно защитить на 100%**. Владелец сервера физически может прочитать любой файл и память процесса. Реалистичная цель другая: сделать извлечение настолько дорогим, что оно бессмысленно, а если оно всё же случилось — доказать это юридически.

## Решение

### Процедура «Выпуск на свободу»

Запускается из Платформы. Каждый шаг фиксируется в журнале.

1. **Сборка для передачи** (см. ниже) под текущие версии ячейки.
2. **Отключение связей:** agent удаляется, телеметрия выключена, адреса Платформы удалены из конфигурации.
3. **Отзыв доступов агентства:** токены, SSH-сертификаты, FTP-пользователи (ADR-004).
4. **Перевыпуск всех секретов:** пароли БД, ключи JWT, ключи шифрования. Даже если что-то осталось у агентства, к системе клиента это больше не подходит.
5. **Лицензии передачи:** купленные модули получают бессрочную лицензию с флагом `exit: true`, привязанную к домену (ADR-008).
6. **Закалка безопасности** и отчёт о проверке:
   - обновлённые зависимости и скан уязвимостей;
   - обязательная двухфакторная аутентификация для администраторов;
   - ограничение попыток входа;
   - защитные HTTP-заголовки;
   - отсутствие учёток по умолчанию;
   - настроенные автобэкапы.
7. **Архив передачи:**
   - образы (`docker save`), `compose.yml`, `.env`;
   - дамп БД и медиа;
   - исходный код уникального сайта клиента;
   - инструкция по запуску и восстановлению;
   - отчёт безопасности.
8. **Акт передачи** с прекращением поддержки. Учётные данные клиента передаются ему и уничтожаются у агентства.

### Четыре слоя защиты кода

**Слой 1. Не отдавать главное (самый надёжный).** Сборка для передачи содержит **только рантайм** одной инсталляции:

| Остаётся у агентства | Уходит клиенту |
|---|---|
| Платформа, маркет, каталог, CA, ключи подписи | Ядро ячейки (сборка) |
| Agent, система обновлений, установщик, CLI разработчика | Купленные модули (сборка) |
| Мигратор WordPress, стартеры, инструменты ИИ-разработки | Сайт клиента (исходники) |
| Исходники ядра и модулей, тесты, исходные миграции | Данные клиента |
| Модули, которые клиент не покупал | — |

Даже полностью разобрав сборку, клиент получает одну рабочую инсталляцию, а не платформу.

**Слой 2. Затруднить чтение:**

- только собранный код, без исходников и source maps;
- минификация и обфускация серверного кода модулей;
- **ценная логика** (`module/protected/`, ADR-003) компилируется в байт-код V8 (bytenode) или в WebAssembly (Rust или Go). Обратно в читаемый код такое практически не превращается;
- минимальный образ без shell и лишних утилит.

Цена: обфускация немного замедляет код и усложняет отладку. Применяется только к коду модулей, производительность проверяется бенчмарком в CI.

**Слой 3. Привязка и метки:**

- лицензия передачи привязана к домену и проверяется офлайн. Перенести админку на другой проект можно только взломав код;
- **водяной знак сборки:** в каждую сборку встраивается уникальный отпечаток клиента. Если модуль всплывёт у кого-то ещё, известно, из какой передачи он ушёл.

**Слой 4. Юридический:**

- клиент получает **лицензию на использование**, а не исключительное право на админку и модули. Копирование, перепродажа, доработка и использование на других проектах запрещены;
- **исключительное право на уникальный сайт** — по договору разработки (как правило, переходит клиенту);
- **оговорка:** статья 1280 ГК РФ разрешает пользователю декомпиляцию для обеспечения совместимости, и договором это полностью не запретить. Поэтому технические слои 1–3 обязательны. **Формулировки договора согласовываются с юристом.**

### Что клиент получает и чего не получает

| Получает | Не получает |
|---|---|
| Работающий сайт и админку | Исходники админки и модулей |
| Исходный код своего сайта, может его менять | Возможность дорабатывать админку |
| Все свои данные с экспортом в открытый формат (JSON, CSV, медиа файлами) | Платформу, маркет, обновления, поддержку |

Экспорт данных всегда доступен. Клиент не становится заложником, и это снимает юридические и репутационные риски.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Передавать исходники всего | Противоречит требованию владельца о защите кода |
| Оставлять онлайн-зависимость от Платформы после передачи | Противоречит требованию удалить все связи. Агентство продолжает отвечать за чужую систему |
| Только юридическая защита | Ст. 1280 ГК РФ, сложно доказать факт извлечения кода |
| Шифрование кода с ключом в памяти | Ключ всё равно на сервере клиента. Сложность без реального выигрыша по сравнению со слоями 1–3 |

## Последствия

- **Сборка для передачи — отдельная цель сборки с первого дня** (`build:exit`). Её работоспособность проверяется в CI: поднять архив в чистом окружении → smoke-тест.
- Модули с самого начала разделяют обычную и защищённую логику (ADR-003).
- Нужен шаблон договора и акта передачи (юрист).
