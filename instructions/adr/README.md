# Архитектурные решения (ADR) — платформа adminpanelOS v2

Набор решений для новой версии платформы. Решения приняты по итогам обсуждения и утверждены владельцем продукта 2026-10-29.

**Правило работы:** сначала теория и согласование ADR, затем реализация. Изменение утверждённого решения оформляется новым ADR, который заменяет старый.

## Что мы строим

Платформа для клиентов агентства. Ключевые требования:

- каждый клиент получает свой уникальный сайт и админку на нашем или своём сервере;
- функционал подключается модулями, как плагины в WordPress, через маркет: покупка, установка в один клик, заказ уникального модуля;
- агентство видит здоровье всех проектов, обновляет их и выдаёт доступы из раздела «Платформа» в CRM renoteOS;
- отказ любой части не роняет остальное;
- текущие клиенты на WordPress сначала берутся под управление, затем переносятся на платформу;
- при уходе клиент получает рабочую систему без связей с платформой, а код агентства защищён.

## Глоссарий

| Термин | Значение |
|---|---|
| **Платформа** | Раздел в CRM renoteOS для управления серверами, сайтами, ячейками, доступами, релизами, лицензиями и маркетом |
| **Ячейка** | Изолированная установка одного клиента: ядро, сайт, worker, БД. Отдельный compose-проект |
| **Ядро** | API и админка ячейки (основа выбирается в ADR-010) |
| **Модуль** | Подключаемый функционал с манифестом, лицензией и собственными данными |
| **Узел** | Сервер с Docker и agent: наше железо, облако или сервер клиента |
| **Agent** | Процесс на узле. Забирает желаемое состояние у Платформы и приводит к нему ячейки |
| **fleet-gateway** | Отдельный процесс renoteOS для связи с agent'ами |
| **Уровень подключения** | L0–L3: что агентство может делать с сайтом в зависимости от доступа |
| **Цель выкладки** | Куда и как публикуется сайт: токен, SSH, SFTP/FTPS, git |
| **Выпуск на свободу** | Процедура передачи проекта уходящему клиенту |

## Атрибуты качества (в порядке приоритета)

| # | Атрибут | Измеримая цель |
|---|---|---|
| 1 | Изоляция отказов | Падение модуля, ядра, Платформы или CRM не останавливает публичный сайт. Ячейки не влияют друг на друга |
| 2 | Безопасность и изоляция данных | Ни один доступ не выходит за границы своей ячейки |
| 3 | Скорость развёртывания | Ячейка ≤ 5 мин, обновление ≤ 2 мин с автооткатом |
| 4 | Передаваемость | Архив передачи поднимается в чистом окружении одной командой |
| 5 | Расширяемость | Новый модуль без изменения ядра |
| 6 | Стоимость | Ячейка ≤ 700 МБ RAM в простое |
| 7 | Сопровождаемость | Обновления не ломают модули: semver и тесты совместимости |

## Дорожная карта

Команда: один разработчик и ИИ. Сроки ориентировочные.

| Этап | Срок | Результат | ADR |
|---|---|---|---|
| **0. Решения** | 1–2 нед. | Утверждённые ADR, недельная проверка Payload, вердикт по ядру, репозиторий и CI | 010, 011 |
| **1. Платформа в renoteOS** | 3–4 нед. | Серверы и сайты, хранилище доступов, SSH-операции, управление WordPress, бэкапы, аудит плагинов. **Первая польза** | 001, 004, 005, 007 |
| **2. Ядро ячейки** | 4–6 нед. | Ядро и модули `seo`, `redirects`, `legal`, `forms`. Стартер сайта, образы, bootstrap, agent | 002, 003, 005, 006 |
| **3. Мигратор WordPress** | 3–4 нед. | Перенос пилотного сайта без потери SEO | 007 |
| **4. Лицензии и маркет** | 3–4 нед. | Покупка счётом и онлайн, установка в один клик, заказ модуля | 008 |
| **5. Передача** | 2 нед. | `build:exit`, процедура «Выпуск на свободу», отчёт безопасности | 009 |
| **6+. Расширение** | постоянно | Модули по данным аудита плагинов. Магазин — отдельным крупным этапом | 003 |

## Главные риски

1. **Эффект второй системы.** Противоядие — вертикальный срез: один сайт проходит всю цепочку (ячейка → контент → публикация → обновление → передача), и только потом расширяемся вширь.
2. **Распределённый монолит.** Противоядие — строгое владение данными (ADR-001) и асинхронные связи (ADR-002).
3. **Слишком общий модульный API на старте.** Точки расширения выводятся из первых реальных модулей (ADR-003).
4. **Утечка учётных данных клиентов.** Envelope encryption, ключи вместо паролей, аудит (ADR-004).
5. **Зависимость от стороннего ядра.** Модули работают только через наш SDK, версия ядра фиксирована (ADR-010).
6. **Объём магазина.** Не начинать, пока не стабилизированы ядро и обновления.

## Открытые вопросы

- Платёжный провайдер для онлайн-оплаты (ЮKassa, CloudPayments или СБП) — выбор на этапе 4.
- Источник данных об уязвимостях WordPress — выбор на этапе 1.
- Провайдер облака и S3-хранилища в РФ — до начала этапа 2.
- Шаблоны договора и акта передачи — нужен юрист до этапа 5.
