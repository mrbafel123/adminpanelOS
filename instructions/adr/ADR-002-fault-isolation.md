# ADR-002. Изоляция отказов и модель процессов ячейки

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-001, ADR-003, ADR-006

## Контекст

Главное требование владельца: если что-то отвалилось, это не должно тащить за собой всю систему.

Буквальная реализация «каждый модуль — отдельный микросервис» на каждой клиентской установке означает:

- 20 и более контейнеров на клиента, 2–4 ГБ RAM на ячейку;
- распределённые транзакции между страницами, SEO и медиа;
- кратный рост точек отказа;
- практически невозможную передачу проекта клиенту (ADR-009).

Для команды из одного разработчика такую систему не сопровождать.

## Решение

Изолируем отказы **по границам, где сбои реально случаются**. Получается модульный монолит, из которого рискованные части вынесены в отдельные процессы. Изоляция работает на трёх уровнях.

### Уровень 1. Платформа целиком

Ячейки, `fleet-gateway`, CRM и серверы независимы друг от друга. Связь между ними асинхронная и переживает недоступность другой стороны.

### Уровень 2. Процессы внутри ячейки

| Процесс | Назначение | Если упадёт |
|---|---|---|
| **site** | Уникальный фронтенд клиента (Node.js) или статическая сборка | Прокси отдаёт последнюю закэшированную версию (`stale-if-error`) |
| **core** | Ядро: API и админка (в Payload это один процесс, ADR-010) | Сайт работает из кэша или статики. Админка недоступна, в Платформе открывается инцидент |
| **worker** | Очереди: публикация, отправка форм, интеграции, письма | Задачи остаются в очереди в БД и выполняются после перезапуска |
| **postgres** | БД ячейки | Как при падении core. Сайт работает из кэша |
| **mod-\*** (опционально) | Тяжёлые и сторонние модули в отдельном контейнере (ADR-003) | Отключается только функция модуля |

Общие на сервер (не на ячейку): прокси Caddy с авто-TLS и кэшем, agent, шлюз доступа SFTPGo (ADR-004), MinIO для медиа и бэкапов.

**Очереди и outbox хранятся в Postgres ячейки** (встроенные jobs ядра или `pg-boss`). Отдельный Redis на ячейку не нужен: на один движущийся элемент меньше, и событие пишется в одной транзакции с данными.

### Уровень 3. Модули внутри core

- **Безопасная загрузка (safe mode).** Каждый модуль инициализируется изолированно, с таймаутом. Если модуль упал при старте, он помечается `failed`, а ядро поднимается без него. Это аналог Recovery Mode в WordPress.
- **Бюджет на синхронные хуки** (filters): по умолчанию 50 мс. Превышение или исключение означает, что вклад модуля пропускается, а не роняет запрос. Модуль получает статус `degraded`.
- **Kill switch.** Платформа может удалённо выключить версию модуля на всём флоте.

### Обязательные паттерны

- Таймаут на каждом внешнем вызове.
- Повторы с экспонентой и jitter, только для идемпотентных операций.
- Ключ идемпотентности на командах: публикация, покупка, отправка формы, выкладка.
- **Transactional outbox** для всех событий за пределы процесса.
- **Circuit breaker** на вызовы контейнерных модулей и внешних API.
- **Очередь недоставленных сообщений** (DLQ), видимая в Платформе.

### Модель здоровья

У каждого процесса и модуля три уровня состояния:

- `live` — процесс жив;
- `ready` — готов принимать запросы;
- `degraded` — работает частично, **с указанием причины**.

Пример статуса в Платформе: «работает, модуль forms деградировал: Telegram API недоступен 12 мин».

### Матрица деградации

| Отказ | Поведение |
|---|---|
| core или БД ячейки | Сайт отвечает из кэша прокси или статики. Админка показывает «режим только чтения» либо недоступна. Открывается инцидент |
| Модуль in-process | Модуль `degraded`, его блоки на сайте показывают fallback, остальное работает |
| Контейнерный модуль | Размыкается circuit breaker, функция модуля недоступна |
| worker | Задачи копятся в БД, отправка форм не теряется |
| fleet-gateway или CRM | Ячейки работают автономно, agent копит телеметрию, лицензии проверяются офлайн |
| Внешний хостинг при выкладке | Публикация остаётся в очереди с повторами, статус виден в админке |
| Соседняя ячейка на сервере | Не влияет: лимиты CPU и RAM, отдельные сети и БД |

### Бюджет ресурсов

Ячейка в простое — **не более 700 МБ RAM**, цель — 20–30 ячеек на сервере с 16–32 ГБ. Лимиты задаются в compose каждой ячейки.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Микросервис на каждый модуль | Расход ресурсов, сложность, невозможность передачи. Не по силам команде |
| Один процесс на всё (как в старом AdminpanelOS) | Падение любого модуля роняет сайт |
| Kubernetes (k3s) | Тяжёлый для одного разработчика и для передачи клиенту. Пересмотреть при количестве ячеек больше 100 |

## Последствия

- Сайт обязан уметь работать из кэша. Для этого нужны правильные заголовки кэширования и ISR в стартере (ADR-005).
- Каждый модуль описывает свой сценарий деградации: это часть Definition of Done (ADR-003).
- Нужны chaos-тесты: остановить core, worker, контейнер модуля и проверить, что сайт отвечает.
