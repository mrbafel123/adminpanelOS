# ADR-001. Состав системы и границы ответственности

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-002, ADR-005, ADR-006, ADR-008

## Контекст

Продукт состоит из двух частей:

1. **Клиентская часть.** Сайт и админка, которые разворачиваются на каждого клиента.
2. **Управляющая часть.** Через неё агентство видит все установки, обновляет их, продаёт модули и выдаёт доступы.

Решения владельца продукта:

- управляющая часть — это **отдельный блок внутри CRM renoteOS**, а не самостоятельный продукт;
- команда — один разработчик и ИИ, поэтому любое дублирование функций стоит дорого;
- в renoteOS уже есть клиенты, проекты, счета (`Invoice`), тревоги с цепочкой эскалации, мониторинг сайтов через Uptime Ray и клиентские аккаунты (`ClientAccount`).

## Решение

### Два репозитория

| Репозиторий | Что в нём |
|---|---|
| **renoteOS** | Раздел **«Платформа»**: серверы, ячейки, доступы, здоровье, инциденты, релизы, лицензии, каталог маркета, управление WordPress-сайтами |
| **adminpanelOS** (`git@github.com:mrbafel123/adminpanelOS.git`) | Всё, что работает у клиента: ядро ячейки (CMS + админка), модули, SDK, стартер сайта, agent, CLI `renote`, сборка для передачи |

### Раздел «Платформа» внутри renoteOS

| Часть | Где | Зачем отдельно |
|---|---|---|
| UI раздела | `apps/web`, новый раздел | Сотрудники работают в одном окне с CRM |
| Бизнес-логика | `apps/api`, модуль `platform` | Использует проекты, клиентов и счета CRM напрямую |
| Приём телеметрии и выдача желаемого состояния | **Отдельный процесс** `apps/fleet-gateway` | Поток heartbeat от всего флота не нагружает CRM. Падение CRM не обрывает связь с ячейками (ADR-002) |
| Фоновые задачи (provisioning, бэкапы и обновления WordPress по SSH) | `apps/worker`, очереди `platform-*` | Долгие операции не блокируют API |
| Данные | Отдельная схема Postgres `platform` | Чёткое владение, независимые миграции |

### Владение данными

Каждая сущность имеет ровно одного владельца. Остальные хранят только ссылку на неё.

| Владелец | Сущности |
|---|---|
| CRM (renoteOS) | Клиент, Проект, Договор, Счёт, Сотрудник, Задача, Тревога, Лид |
| Платформа (renoteOS, схема `platform`) | Сервер, Сайт, Подключение, Учётные данные, Ячейка, Желаемое состояние, Инцидент, Релиз, Раскатка, Модуль, Версия модуля, Лицензия, Доступ |
| Ячейка (adminpanelOS) | Контент и данные модулей конкретного клиента, локальные токены и журнал аудита |

Ячейка ссылается на проект CRM через `crmProjectId`, Платформа — через `projectId` из CRM.

### Взаимодействие

- **Между ячейкой и Платформой** — только через agent и `fleet-gateway` по HTTPS. Ячейка всегда инициирует соединение сама (pull), входящих портов у сервера нет.
- **Между модулем `platform` и остальной CRM** — через внутренние сервисы и события. Таблицы других модулей CRM не читаются напрямую.
- **Общие контракты** (события, желаемое состояние, манифест модуля, формат лицензии) лежат в пакете `@renote/platform-contracts` в репозитории adminpanelOS. Пакет публикуется в GitHub Packages и подключается в renoteOS как версионированная зависимость.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Studio — отдельный продукт со своей БД и UI (как в старом AdminpanelOS) | Дублирует клиентов, проекты, счета и тревоги CRM. Сотрудникам нужны два интерфейса |
| Всё внутри процесса `apps/api` renoteOS | Телеметрия флота и долгие SSH-операции конкурируют с CRM за ресурсы. Падение одного роняет другое |
| Один монорепозиторий для CRM и платформы | Код, уходящий клиенту при передаче (ADR-009), должен быть физически отделён от кода агентства |

## Последствия

- Деплой renoteOS теперь включает раздел «Платформа». `fleet-gateway` деплоится и перезапускается независимо.
- Нужна дисциплина версий у `@renote/platform-contracts`: изменения только совместимые, с контрактными тестами (ADR-003).
- Старый `studio-api` и `studio-admin` не развиваются. Из них берутся только контракты и идеи (ADR-011).
