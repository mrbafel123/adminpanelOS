# ADR-003. Модульный контракт

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-002, ADR-008, ADR-009, ADR-010

## Контекст

Любой функционал сверх ядра — это модуль. Клиент подключает и покупает модули так же, как плагины в WordPress. Агентство разрабатывает модули под заказ, и они потом попадают в маркет.

Ограничения из других решений:

- модуль не должен ронять ядро (ADR-002);
- модуль должен лицензироваться и блокироваться (ADR-008);
- ценная логика модуля должна защищаться при передаче (ADR-009).

## Решение

### Манифест

Каждый модуль описывается манифестом `module.yaml`:

```yaml
id: forms                      # уникальный, kebab-case
version: 1.4.0                 # semver
core: ">=1.2 <2.0"             # совместимые версии ядра
requires: { media: "^1.0" }    # зависимости, проверка на циклы
runtime: inprocess             # inprocess | container
permissions:                   # что модулю разрешено
  - mail.send
  - events.publish:forms.*
  - http.outbound:api.telegram.org
settings: ./settings.schema.json   # из неё автоматически строится форма в админке
admin:
  menu: [{ id: forms, title: "Формы", icon: inbox }]
site:
  blocks: [form]               # блоки и компоненты для сайта
  routes: ["/api/forms/*"]     # публичные эндпоинты
migrations: ./migrations
events:
  emits: [forms.submitted.v1]
  consumes: []
license: { model: subscription, sku: forms-pro }   # или free
degradation: "Формы принимаются в очередь, уведомления откладываются"
```

### Жизненный цикл

`install → migrate → activate → (degraded) → deactivate → uninstall`, плюс `upgrade`.

- Каждый шаг **идемпотентен**: повтор после сбоя безопасен.
- `uninstall` по умолчанию **сохраняет данные** модуля. Удаление данных — отдельное явное действие с бэкапом.
- `upgrade` выполняет миграции по схеме expand / contract (ADR-006).

### Точки расширения

Идея actions и filters из WordPress, но типизированно и с изоляцией.

| Тип | Как работает | Защита |
|---|---|---|
| **Actions** (события после факта, `page.published.v1`) | Асинхронно через outbox и очередь | Подписчик падает отдельно, с повторами и DLQ |
| **Filters** (синхронная трансформация, `seo.meta.resolve`) | Цепочка обработчиков в запросе | Бюджет 50 мс, ошибка или превышение означают пропуск вклада (ADR-002) |
| **Contributions** (декларативные вклады из манифеста) | Коллекции и поля контента, блоки, пункты меню, страницы настроек, роли и скоупы | Валидация манифеста при установке |

Список точек расширения **не придумывается заранее**. Он выводится из первых 5–6 реальных модулей (SEO, формы, редиректы, legal, счётчики, cookie) и затем фиксируется в SDK.

### Владение данными модуля

- Данные модуля лежат в его собственном пространстве имён: отдельная схема Postgres `mod_<id>` или префикс таблиц, в зависимости от выбора ядра (ADR-010).
- **Модуль не читает и не пишет чужие таблицы.** Доступ к другому модулю — только через его публичный сервис в SDK или через его события.
- Благодаря этому любой модуль можно позже вынести в контейнер без переписывания.

### Два режима исполнения

| `runtime` | Для чего | Изоляция |
|---|---|---|
| `inprocess` | Наши официальные модули: SEO, формы, legal, счётчики | Safe mode, бюджеты, kill switch |
| `container` | Тяжёлые модули (магазин, обмен с 1С), **любой код не от агентства**, кастомные модули под одного клиента | Отдельный контейнер и сеть. Нет доступа к БД ядра, только SDK по HTTP со скоупами |

### UI модулей в админке

1. **По умолчанию — UI из схемы.** Форма настроек строится из JSON Schema, коллекции контента — средствами ядра. Покрывает около 80% модулей.
2. **Свои страницы на React** — только у официальных модулей, подписанных агентством.
3. **Сторонние модули** — iframe-песочница с мостом `postMessage` (тема, авторизация, навигация).

### Защита кода (связь с ADR-009)

У модуля две части:

- `module/` — манифест, схемы, UI, связка с ядром. Обычная сборка.
- `module/protected/` — ценная бизнес-логика. Собирается отдельно с обфускацией, в байт-код V8 или в WebAssembly.

### Версионирование и совместимость

- Ядро и модули живут по semver. Публичный API ядра нельзя удалить без предупреждения: сначала он помечается устаревшим минимум на один минорный релиз.
- В CI каждая версия модуля тестируется против двух версий ядра: N-1 и N.
- Контракты событий версионируются в имени (`.v1`, `.v2`). Изменения внутри версии — только добавление полей.

### Поставка

Сборка в CI → SBOM → подпись артефакта → публикация в каталог Платформы. **Ячейка устанавливает только модули с валидной подписью** (ADR-008).

### Definition of Done для модуля

- манифест прошёл валидацию;
- миграции работают в обе стороны;
- есть схема настроек;
- сценарий деградации описан и проверен тестом;
- тесты совместимости с ядром N-1 и N проходят;
- лицензирование подключено (или модуль явно `free`);
- есть документация для админки и для разработчика сайта.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Хуки как в WordPress: глобальные и нетипизированные | Модули ломают друг друга, ошибки находятся только в рантайме |
| Все модули в контейнерах | Расход ресурсов (ADR-002) |
| Module Federation для всех модулей | Чужой код исполняется в админке, хрупкая зависимость от версий React |
| Модули как npm-пакеты без манифеста | Нет управления совместимостью, правами и лицензиями |

## Последствия

- Нужен пакет `@renote/module-sdk`: типы манифеста, точки расширения, клиент для контейнерных модулей, тестовый стенд.
- Перед публикацией в маркет у модуля обязательны ревью и подпись.
- Первые модули делаются переносом логики из старого кода (ADR-011), и на них проверяется сам контракт.
