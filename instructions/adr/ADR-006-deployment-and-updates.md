# ADR-006. Развёртывание ячеек и обновления

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-001, ADR-002, ADR-005, ADR-011

## Контекст

Распаковка системы на сервере должна быть быстрой, простой и мобильной. Сейчас (в старом AdminpanelOS) деплой выполняется сборкой на сервере, через PM2 и ручные shell-скрипты.

Цели:

- **новая ячейка ≤ 5 минут**;
- **обновление ячейки ≤ 2 минут** с автоматическим откатом.

## Решение

### Образы

- CI (GitHub Actions) собирает образы `core`, `site-runtime`, `worker`, `toolbox`, `agent` и публикует их в приватный GHCR с тегом версии.
- **На сервере ничего не собирается**, только `docker pull`. Это главное ускорение.
- Код сайта клиента собирается в CI его репозитория в образ или статический архив (ADR-005).

### Подготовка сервера (один раз)

Скрипт `bootstrap`:

1. Устанавливает Docker.
2. Ставит прокси Caddy (авто-TLS), SFTPGo, MinIO и agent.
3. Включает firewall: открыты только 80, 443 и SSH администратора.
4. Регистрирует сервер в Платформе по одноразовому токену.

Одинаково работает на нашем железе, в облаке и на сервере клиента с root (уровень L3).

### Создание ячейки

`renote cell create` — команда или кнопка в Платформе. Шаги:

1. Сгенерировать секреты (БД, JWT, ключ шифрования).
2. Положить `compose.yml` и `.env` ячейки из шаблона.
3. `pull` и `up`.
4. Миграции ядра и модулей.
5. Пресет (набор модулей) и демо-контент.
6. Первый администратор, ссылка-приглашение уходит в CRM.
7. Маршрут в Caddy и выпуск TLS-сертификата.
8. Регистрация ячейки в Платформе.

Каждая ячейка — это отдельный compose-проект со своей Docker-сетью, своей БД и лимитами CPU и RAM.

### Желаемое состояние и agent-reconciler

Платформа не отправляет на серверы команды. Она хранит **желаемое состояние** каждой ячейки:

```yaml
cell: client-a
core: 1.6.2
modules: { seo: 2.1.0, forms: 1.4.0 }
resources: { memory: 768M, cpus: 1.0 }
deployTargets: [ { driver: sftp, host: example.ru, secretRef: cred_123 } ]
backups: { daily: true, retentionDays: 14 }
```

**Agent на сервере работает как reconciler** (по принципу контроллера Kubernetes, но без Kubernetes):

1. Раз в 30–60 секунд забирает желаемое состояние из `fleet-gateway`. Только pull, входящих портов нет.
2. Сравнивает его с фактическим и вычисляет разницу.
3. Применяет разницу шагами машины состояний обновления.
4. Отправляет фактическое состояние и телеметрию.

Что это даёт:

- **Повторяемость.** Любую ячейку можно воссоздать из описания и бэкапа. Это и восстановление после сбоя, и переезд, и передача клиенту.
- **Видимость дрейфа.** Ручные изменения на сервере обнаруживаются и показываются в Платформе.
- **Раскатки** превращаются в правку желаемого состояния у группы ячеек.

### Машина состояний обновления

Берётся из старого `apps/update-builder/src/lifecycle.ts` (ADR-011):

`PENDING → PREFLIGHT → DOWNLOADING → BACKUP_DB → MIGRATING → SWAPPING → SMOKING → COMPLETED`

Любая ошибка ведёт в `FAILED_*`, а после неё в `ROLLED_BACK`: восстановление БД из снапшота и возврат образа.

### Раскатки по кольцам

`internal → pilot → 10% → all`.

- Переход к следующему кольцу — автоматически после окна наблюдения (по умолчанию 24 часа) без роста ошибок.
- При росте ошибок раскатка останавливается автоматически.
- Kill switch модуля (ADR-003) действует сразу на всех кольцах.

### Миграции БД без простоя

Правило **expand / contract**:

1. Добавить новую колонку или таблицу.
2. Писать в старую и новую.
3. Перенести данные.
4. Переключить чтение на новую.
5. Удалить старую — **только в следующем релизе**.

Без этого правила откат образа ломается о несовместимую схему.

### Бэкапы

- Ежедневно `pg_dump` и медиа отправляются в S3-хранилище в РФ: MinIO на отдельном узле или облачное S3.
- Хранение 14 дней по умолчанию.
- **Снапшот перед каждым обновлением.**
- Платный тариф: WAL-G с восстановлением на любую точку во времени.
- **Ежемесячная автоматическая проверка восстановления**: бэкап случайной ячейки поднимается во временной ячейке и проходит smoke-тест. Непроверенный бэкап не считается бэкапом.

### Окружения

dev (локальный compose) → staging-ячейки на отдельном узле → кольца продакшена.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Сборка на сервере + PM2 (как сейчас) | Медленно, нет изоляции, нет повторяемости |
| Kubernetes (k3s) | Избыточен для одного разработчика и для передачи клиенту (ADR-002) |
| Push-команды из Платформы на серверы по SSH | Нужны входящие порты и постоянные ключи, нет сверки состояния |
| Ansible как основной инструмент | Подходит для `bootstrap`, но не для постоянной сверки состояния |

## Последствия

- Agent — критичный компонент. Его обновление должно иметь собственный откат (двухфазная замена бинарника).
- Тест обновлений N-1 → N на данных каждого пресета — обязательная проверка в CI (ADR-003).
- `compose.yml` ячейки — это контракт: он же используется в архиве передачи (ADR-009).
