# ADR-005. Серверы, уровни подключения и выкладка сайтов

- **Статус:** утверждено 2026-10-29
- **Дата:** 2026-10-29
- **Связанные:** ADR-004, ADR-006, ADR-007

## Контекст

Сценарии размещения:

- **A.** Купленное агентством железо, на нём ячейки клиентов.
- **B.** Облачный сервер, тот же принцип ячеек.
- **C.** Текущие клиенты на своих серверах. Доступ по SSH-ключам или только по FTP. Большинство таких сайтов — на WordPress.

Все серверы находятся в РФ (152-ФЗ).

Сайты агентства — всегда уникальная разработка (WordPress или Node.js + уникальный дизайн, часто с помощью ИИ). Конструктор не используется.

## Решение

### Сервер — это узел, неважно какой

Для системы A и B одинаковы: это узел, на котором стоят Docker и agent. Переезд ячейки между железом и облаком — штатная операция «бэкап → создать на новом узле → восстановить → переключить DNS».

### Уровни подключения

Каждому сайту и серверу в Платформе присваивается уровень. Уровень определяет, какие функции доступны.

| Уровень | Что есть | Как управляем |
|---|---|---|
| **L3. Управляемый узел** | Наш, облачный или клиентский сервер с root: Docker + agent | Ячейки, обновления, бэкапы, полная телеметрия |
| **L2. SSH-оператор** | SSH без права ставить ПО, либо старый стек | Worker Платформы выполняет команды по SSH по расписанию и по кнопке |
| **L1. Только FTP** | Только файловый доступ (FTPS/SFTP) | Выкладка файлов сайта, бэкап файлов |
| **L0. Только наблюдение** | Доступа нет | Внешний мониторинг через Uptime Ray в CRM |

Матрица возможностей:

| Функция | L3 | L2 | L1 | L0 |
|---|---|---|---|---|
| Мониторинг доступности | ✅ | ✅ | ✅ | ✅ |
| Внутренние метрики (CPU, RAM, диск, БД) | ✅ | 🟡 по SSH | — | — |
| Бэкап БД | ✅ | ✅ | — | — |
| Бэкап файлов | ✅ | ✅ | ✅ | — |
| Управление WordPress (ADR-007) | ✅ | ✅ | — | — |
| Выкладка сайта на нашей платформе | ✅ SSR | ✅ статика или SSR | ✅ статика | — |
| Ячейка с нашей админкой | ✅ | — | — | — |

Повышение уровня (например, с L2 до L3 после установки agent) — отдельная услуга. **Текущие клиенты заводятся в систему сразу, без обязательного переезда.**

### Модель данных в Платформе

```
Server (узел; провайдер, IP, уровень, ресурсы)
  └─ Site (сайт; домен, стек: wordpress | node | static | other, crmProjectId)
       ├─ Connection (способ подключения: ssh | sftp | ftps | agent | token)
       │    └─ Credential (зашифровано, ADR-004)
       └─ Cell (ячейка, если сайт на нашей платформе)
```

### Подключение сайта к админке: цели выкладки

Сайт — это уникальный фронтенд. Он получает контент из ядра ячейки. Как именно — определяет **цель выкладки** (Deploy Target) с драйвером:

| Драйвер | Механика | Когда |
|---|---|---|
| `token` (pull) | Сайт сам забирает контент из Public API по service-токену. Изменения доставляются через ISR и webhook на revalidate | Сайт в ячейке или на любом Node-хостинге. **Режим по умолчанию** |
| `ssh` (push) | Сборка → `rsync` → команда после деплоя → проверка | Сервер или VPS клиента |
| `sftp` / `ftps` (push) | Сборка статики → загрузка | Shared-хостинг без Node.js |
| `git` (push) | Коммит сборки в репозиторий, дальше её подхватывает CI | Клиенты со своей командой разработки |

**Режим рендеринга выбирается автоматически по уровню:**

- L3 и L2 с возможностью запускать Node.js — **SSR** (динамический сайт).
- L1 и L2 без Node.js — **статическая сборка**. Формы, поиск и другая динамика ходят в API ячейки.

Разработчик пишет сайт один раз на стартере. Способ выкладки определяется сервером.

### Требования к выкладке

- **Выкладка — задача в очереди**, а не синхронный вызов. Шаги: build → upload → verify → switch. Задача идемпотентна, с повторами.
- **Атомарность.** Файлы заливаются в `releases/<id>/`, затем переключается симлинк. Где симлинков нет: файлы с хешами в именах, `index.html` загружается последним.
- **Инкрементальность.** Храним манифест хешей прошлой выкладки, загружаем только изменившиеся файлы.
- **Проверка.** После switch — HTTP-проверка ключевых страниц. При ошибке автоматический откат на предыдущий release.
- **Откат** вручную или автоматически — переключение на предыдущий release.

### Стартер сайта

`starters/site-node` в adminpanelOS:

- Next.js с типизированным SDK, сгенерированным из модели контента ячейки;
- готовые ISR и заголовки кэширования для работы при падении ядра (ADR-002);
- поддержка двух режимов сборки: SSR и static export;
- инструкции для ИИ-агентов (`CLAUDE.md`, описание SDK), чтобы новые сайты собирались быстро и без ошибок интеграции.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Требовать переезд всех клиентов в ячейки до подключения | Блокирует работу с текущими клиентами на месяцы |
| Только SSR | Не работает на shared-хостингах с одним FTP |
| Только статика | Медленная публикация, нет динамики без API |

## Последствия

- Драйверы выкладки и SSH-операции живут в worker Платформы и в worker ячейки. У них общий пакет `@renote/deploy-drivers`.
- В CI нужны тестовые SFTP-, FTPS- и SSH-серверы для проверки драйверов, в том числе с обрывом связи посередине выкладки.
